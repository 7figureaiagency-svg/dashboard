# Plan 33.5: Conversational Context Recap Card, Visit Time Anchor & Voice Script Normalization

<objective>
Resolve all 4 bugs and enhancements identified in production Telegram testing:
1. Fix `parseVisitSlot` to prevent option references ("option 1") from being misparsed as visit hours, ensuring "option 1 ke sath kal 10 baje" books strictly at 10:00 AM IST instead of 1:00 PM.
2. In `voice_decoder.ts`, prevent Groq Whisper from outputting in Perso-Arabic / Urdu script by adding prompt steering and an automatic sub-200ms Urdu-to-Latin transliteration bridge (`transliterateArabicScriptToLatin`), ensuring voice notes like "mujhe 3 bhk flat chahiye 1 cr budget me alkapuri me" are 100% understood by downstream parsers.
3. Fix invalid Gemini endpoint model names (`gemini-2.5-flash` / `gemini-2.5-pro` -> `gemini-2.0-flash` / `gemini-1.5-pro`) to eliminate HTTP 404 fallback delays.
4. Upgrade `LOCATION_CONFIRMATION` into a comprehensive **Previous Conversation Recap Card** displaying all saved criteria (Location: Alkapuri, Property Type: 3BHK Flat, Budget: ₹1 Cr / ₹10 Cr, Purpose, Timeline) with an interactive 2-choice fork (1 = Proceed with saved details, 2 = Change / update details).
</objective>

<context>
- Telegram test by Manthan revealed that "option 1 ke sath kal 10 baje" booked visit at 1:00 PM because regex `text.match(/(\d{1,2})(?::(\d{2}))?\s*(am|pm|baje|vage)?/i)` matched "1" in "option 1" (since time unit was optional).
- Voice note audio was transcribed acoustically accurately by Groq Whisper, but output in Urdu script (`مجھے 3 بیج کے فلیٹ چاہیے...`) because of Whisper language auto-detection, which prevented keyword/entity extraction.
- In `LOCATION_CONFIRMATION`, only location ("Alkapuri") was shown, without other saved details (budget, BHK, property type), leaving the user uninformed about previous conversation context.
- Gemini endpoints in `cognitive_extractor.ts` and `voice_decoder.ts` called non-existent `gemini-2.5-flash`, causing 2500ms timeout fallbacks.
</context>

<task type="auto">
  <name>Task 1: Visit Slot Option Decoupling & Explicit Time Anchoring</name>
  <files>
    supabase/functions/realtor-lead-engine/index.ts
  </files>
  <action>
    1. In `parseVisitSlot(slotText)`:
       - Strip option references (`\b(?:option|opt|number|no|choice)\s*\d+\b`) from the input before matching hour digits.
       - Prioritize explicit time patterns that contain anchors: `(?:\b(?:at|around|ke|par)?\s*(\d{1,2})(?::(\d{2}))?\s*(?:am|pm|baje|vage|વાગે|બજે|o'?clock)\b)`.
       - If no explicit anchor pattern matches, fall back to searching for a colon format `(\d{1,2}):(\d{2})`.
       - Only if still no match, look for standalone digits that are NOT part of property configurations or option numbers.
    2. In compound booking messages like `"option 1 ke sath kal 10 baje ki visit book kar do"`:
       - Simultaneously extract `selected_option_index: 0` (Option 1) and book at `10:00 am` IST (`04:30:00.000Z` UTC).
  </action>
  <verify>
    Verify `"option 1 ke sath kal 10 baje ki visit book kar do"` extracts 10:00 AM IST (`04:30 UTC`) and option 1.
    Verify `"option 2 sham 5 baje"` extracts 5:00 PM IST (`11:30 UTC`) and option 2.
    Verify `"kal 10 baje"` extracts 10:00 AM IST.
  </verify>
  <done>
    `parseVisitSlot` accurately extracts visit hour without ever colliding with menu option numbers.
  </done>
</task>

       - Change `gemini-2.5-flash` to `gemini-2.0-flash` (with fallback to `gemini-1.5-flash`).
       - Change `gemini-2.5-pro` to `gemini-1.5-pro`.
       - This eliminates HTTP 404 errors and 2.5-second fallback delays.
  </action>
