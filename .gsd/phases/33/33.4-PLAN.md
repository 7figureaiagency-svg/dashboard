# Plan 33.4: Pre-Flight Self-Correction Gate & Codebase Modularization

<objective>
Implement a pre-flight reflection and self-correction gate that validates outbound responses before dispatch (preventing hallucinations, re-asking answered questions, and contradictions), refactor the 12,000-line `realtor-lead-engine/index.ts` into clean Deno modules, deploy version `v86-universal-multimodal-cognitive-agent` to Supabase production, and empirically verify the complete system end-to-end.
</objective>

<context>
- Even advanced LLMs can occasionally hallucinate numbers or overlook a subtle constraint. A lightweight (~100ms) verification gate intercepts any flawed response before it reaches the customer.
- The monolithic 12,000-line `index.ts` makes code reviews difficult and increases regression risk. Breaking it into modular submodules creates an enterprise-grade architecture.
- Multi-tenant WABA safety invariants (20-lead batch caps, 350-550ms jitter delay) and 100% Non-n8n architecture must be strictly preserved.
</context>

  <name>Task 1: Pre-Flight Self-Correction Gate (`verifyOutboundReply`)</name>
  <files>
    supabase/functions/realtor-lead-engine/index.ts
  </files>
  <action>
    1. Implement `verifyOutboundReply(params: { userMessage: string, proposedReply: string, extractedIntent: any, leadState: string, lastBotPrompt: any }): Promise<{ isValid: boolean, correctedReply?: string, reason?: string }>`:
       - Checks the proposed response against 4 critical invariants:
         1. *Contradiction Check:* If user said "bechni hai", does proposed reply talk about buying or commercial leasing?
         2. *Redundancy Check:* Does the proposed reply re-ask for an entity that the user explicitly provided in the immediate message?
         3. *Hallucination Check:* Does the reply invent specific pricing or unconfirmed project names not present in the DB/context?
         4. *Policy Check:* Does the reply include forbidden phrases or violate WABA compliance?
       - If invalid, trigger an instant lightweight corrective re-synthesis with the specific rejection reason.
    2. Hook `verifyOutboundReply` directly into the outbound dispatch pipeline immediately prior to `sendTelegramMessage` and `sendWhatsAppMessage`.
  </action>
  <verify>
    Test `verifyOutboundReply` with deliberate contradiction/redundancy examples to ensure rejection and auto-correction.
  </verify>
  <done>
    Pre-flight verification gate prevents 100% of hallucinations and conversational blunders.
  </done>
</task>
