# Plan 35.1: Enterprise Multi-Tenant Hardening & Zero-Leakage Data Scoping

<objective>
Harden the multi-tenant architecture for 100+ brokerages: eradicate dangerous cross-tenant inventory fallbacks (`eq("client_id", defaultTenantId)`), implement an in-memory LRU tenant configuration cache (sub-1ms tenant lookup), strictly scope all database queries by `activeTenantId`, and establish PostgreSQL composite indexes for ultra-fast query performance at high lead volume.
</objective>

<context>
- Currently in `supabase/functions/realtor-lead-engine/index.ts` line 902, if a tenant has no matching inventory, the query dangerously falls back to `client_id = defaultTenantId` (NextGen Realty), creating a critical cross-tenant data leak.
- On every incoming webhook message, the engine performs 4-5 redundant database roundtrips to fetch client branding, city, bot token, and `bot_knowledge`. Under 100+ tenants, this creates DB connection saturation and increases latency by 200-300ms.
- To support 100+ clients with 500k+ rows, PostgreSQL composite indexes are required on `leads(client_id, lead_id)`, `leads(client_id, status, last_active_at)`, `inventory(client_id, status, property_type)`, and `site_visits(client_id, scheduled_at, status)`.
</context>
