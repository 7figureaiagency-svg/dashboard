# Plan 27.1: Stage-Conditioned Dynamic Micro-Prompts, State Dialect Modules & Ambiguity Disambiguation

<objective>
Refactor the monolithic intent classification engine into a lean core system prompt coupled with dynamic, stage-conditioned micro-prompts (`buildStageMicroPrompt`). Eliminate numeric option collisions (such as '2 BHK' triggering Option 2 in role triage or single digits misfiring across possession, furnishing, and attendance) using boundary-checked token trees and strict stage disambiguation.

Purpose: Reduce inference latency and token overhead by ~55% while elevating intent classification determinism to ~100% across all Indic vernacular dialects (Hinglish, Gujlish, Gujarati script, English).
Output: Lean modular classifier architecture in `supabase/functions/realtor-lead-engine/index.ts` with stage-conditioned micro-prompts and numeric disambiguation guards.
</objective>

    Refactor the intent classification prompt architecture in `supabase/functions/realtor-lead-engine/index.ts`:
    1. **Deconstruct `INTENT_CLASSIFICATION_SYSTEM_PROMPT` into `CORE_INTENT_SYSTEM_PROMPT` (~400 tokens):**
       - Keep only the TypeScript discriminated union definitions (`UserAction`, `IntentResult`).
       - Retain Tier 1 Global Precedence Rules:
         - `OPT_OUT`: Explicit unsubscription phrases only ("stop", "unsubscribe", "not interested", "message mat karo", "band karo").
         - `REQUEST_HUMAN_CALL`: Direct human call requests ("call me", "agent se baat", "phone pe baat karni hai").
         - `BROCHURE_REQUEST`: Direct brochure/catalog asks ("brochure bhej do", "catalog bhejo").
         - `MAP_REQUEST`: Direct location/map asks ("location bhej do", "map link").
         - `ASK_FAQ`: Office address, timings, RERA, brokerage, agency info, or loan questions.
       - Retain strict JSON output format instruction: Generate ONLY valid JSON matching `IntentResult`.
       - Strip out all 27+ static few-shot exemplars and verbose state-specific rule blocks from the global system prompt.
    2. **Implement `buildStageMicroPrompt(lead: any, currentState: string): string` (~350-450 tokens):**
       - Generate targeted stage rules and 2-4 focused few-shot exemplars based on `currentState`:
         - `ROLE_SELECTION_PENDING` / `FRESH`: Focus on 1 (Buy/Rent) vs 2 (Sell/Lease) vs 3 (Both); direct property type queries ("2 BHK", "flat in Gotri", "commercial shop") -> `CHANGE_REQUIREMENT` (SEEKER); direct seller queries ("shop bechni he", "maro flat vechvo che") -> `SUBMIT_LISTING` (OWNER); greeting guard.
         - `OWNER_*_PENDING` (`OWNER_CONFIG_PENDING`, `OWNER_SOCIETY_PENDING`, `OWNER_LOCATION_PENDING`, `OWNER_AREA_PENDING`, `OWNER_PRICE_PENDING`, `OWNER_POSSESSION_PENDING`, `OWNER_FURNISHING_PENDING`, `OWNER_PHONE_PENDING`): Owner intake extraction rules; single-digit mapping for `OWNER_POSSESSION_PENDING` ("1" -> READY_TO_MOVE, "2" -> UNDER_CONSTRUCTION) and `OWNER_FURNISHING_PENDING` ("1" -> UNFURNISHED, "2" -> SEMI_FURNISHED, "3" -> FURNISHED); area unit conversions (1 Var = 9 sqft); phone number extraction (10-digit number into contact_phone, never price/budget); compound society + configuration extraction; allowing Tier 1 FAQs without breaking intake.
         - `QUALIFYING`: Seeker 3-turn compound qualification rules; rental terminology ("bhade", "bhadu", "bhada par", "kiraya", "rent" -> requirement: "RENT"); budget rules (₹1,000 to ₹50,000 monthly rent vs Lakhs/Cr purchase); commercial lease rules.
         - `OPTIONS_SENT` / `VISIT_REQUESTED` / `SITE_VISIT_PROPOSED`: Option selection (0 for 1st, 1 for 2nd, 2 for 3rd); slot booking dates and times ("aaj 6 baje", "Sunday 11 AM", "kal shaam 5 baje", "kale sanje 5 vage").
         - `SITE_VISIT_DONE` / `SITE_VISIT_BOOKED` (post-visit): Attendance survey ("1" -> attended: true, "2" -> attended: false / CANNOT_ATTEND_VISIT); feedback vs alternative options ("Option share karo" -> GENERAL_QUERY request_alternative_options).
         - `CRITERIA_CONFIRMATION_PENDING`: Confirmation ("1" / "ha" / "barobar" -> confirm: true, "2" / "nahi" / "badalna" -> confirm: false).
         - `OWNER_DETAILS_GATHERED`: Decline second listing ("nahi", "nathi karvi" -> GENERAL_QUERY decline, never OPT_OUT) vs listing a 2nd property vs buyer search.
    3. **Update `buildLeadContextForClassifier(lead: any, messageText: string): string`:**
       - Append the stage micro-prompt from `buildStageMicroPrompt(lead, lead?.state)` to user content.
       - Include known entity summaries, active persona, and detour state (`metadata.suspended_state`).
    4. **Wire into `classifyLeadIntentWithGroq` and `classifyLeadIntentWithGemini`:**
       - Pass `CORE_INTENT_SYSTEM_PROMPT` as system message.
       - Pass combined lead context and stage micro-prompt as user content.
       - Maintain fallback compatibility if `lead` or `currentState` is undefined.

    AVOID: Keeping static exemplars for all 10+ states in a single prompt because it causes token bloat (~2,150 tokens) and confuses the LLM on ambiguous numeric inputs.
    USE: Dynamic stage conditioning so the LLM only evaluates exemplars and rules relevant to the active dialog step.

  <name>Implement State-Specific Few-Shot Modules & Zero-Numeric-Collision Token Trees</name>
  <files>supabase/functions/realtor-lead-engine/index.ts</files>
  <action>
    Implement strict numeric disambiguation and boundary-checked token trees in `supabase/functions/realtor-lead-engine/index.ts`:
    1. **BHK Configuration vs Role Option 2 Collision Guard:**
       - In `ROLE_SELECTION_PENDING`, protect against inputs like "2 BHK", "2bhk", "2 bhk flat", "2 bed":
         - Create `isBhkOrPropertyConfiguration(text: string): boolean`: checks `/(?:^|\b)(?:[1-5]\s*bhk|[1-5]\s*rk|flat|apartment|villa|bungalow|penthouse|office|shop|plot)\b/i`.
         - Single "2" or "2️⃣" ONLY routes to Option 2 (OWNER / `SUBMIT_LISTING`) if `!isBhkOrPropertyConfiguration(text)`.
         - If user replies "2 BHK" in `ROLE_SELECTION_PENDING`, immediately classify as `CHANGE_REQUIREMENT` (user_role: "SEEKER", property_type: "2BHK"), NEVER Option 2.
    2. **State-Specific Isolated Single-Digit Disambiguation (`disambiguateNumericChoice`):**
       - Standardize single-digit interpretation across states:
         - In `OWNER_POSSESSION_PENDING`: "1" -> `possession_status = "READY_TO_MOVE"`, "2" -> `possession_status = "UNDER_CONSTRUCTION"`.
         - In `OWNER_FURNISHING_PENDING`: "1" -> `furnishing_status = "UNFURNISHED"`, "2" -> `furnishing_status = "SEMI_FURNISHED"`, "3" -> `furnishing_status = "FURNISHED"`.
         - In `SITE_VISIT_DONE` / post-visit survey: "1" -> `CONFIRM_VISIT_ATTENDANCE` (attended: true), "2" -> `CANNOT_ATTEND_VISIT` (attended: false).
         - In `CRITERIA_CONFIRMATION_PENDING`: "1" -> `CONFIRM_CRITERIA` (confirm: true), "2" -> `CONFIRM_CRITERIA` (confirm: false).
         - In `DUAL_ROLE_MENU_PENDING`: "1" -> List property first (PROVIDER), "2" -> Search properties first (SEEKER).
         - In `OPTIONS_SENT`: "1", "2", "3" -> `SELECT_OPTION` (index 0, 1, 2) or `BOOK_VISIT`.
    3. **Gujarati Vernacular Normalization & Token Trees:**
       - Normalize Gujarati numeral script: map `૧` -> 1, `૨` -> 2, `૩` -> 3, `૪` -> 4, `૫` -> 5 in text pre-processing before token evaluation.
       - Replace loose substring checks with boundary-checked token trees:
         - Rental keywords: `/(?:^|\b)(?:bhade|bhadu|bhada|bhaade|kiraya|kiraye|rent\s*par|bhada\s*par|bhade\s*thi|reva\s*mate)\b/i`.
         - Sale keywords: `/(?:^|\b)(?:vechva|vechvu|vechvo|bechna|bechni|kharidva\s*nathi|sale|bikri)\b/i`.
    4. **Deterministic Fallback Synchronization:**
       - Update the Tier 3 deterministic fallback block in `classifyLeadIntent` to use `disambiguateNumericChoice` and `isBhkOrPropertyConfiguration`.

    AVOID: Using loose substring regexes like `text.includes("2")` or `/2/` because any message containing a digit 2 (such as "2 BHK", "2000 sqft", "25 Lakhs") will falsely trigger Option 2.
    USE: Exact isolated boundary checks `/(?:^|\b)(?:2|2️⃣|two|option\s*2)\b/i` combined with negative lookaheads/guards against BHK and configuration tokens.
