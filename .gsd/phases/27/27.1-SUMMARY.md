# Phase 27.1 Summary: Stage-Conditioned Dynamic Micro-Prompts, State Dialect Modules & Ambiguity Disambiguation

## Execution Overview

Plan 27.1 refactored the real estate lead engine's monolithic intent classification prompt into a lean core system prompt coupled with dynamic, stage-conditioned micro-prompts (`buildStageMicroPrompt`). It eliminated numeric option collisions (such as '2 BHK' triggering Option 2 OWNER in role triage) using boundary-checked token trees and strict stage disambiguation.

- **Target File:** `supabase/functions/realtor-lead-engine/index.ts`
- **Architecture:** 100% Non-n8n (Supabase Edge Function + PostgreSQL + React CRM Dashboard)
- **Status:** Complete

---

## Key Achievements

### 1. Lean Core Intent System Prompt & Stage-Conditioned Micro-Prompts
- **Core System Prompt (`CORE_INTENT_SYSTEM_PROMPT`):**
  - Reduced base prompt token footprint from 2,150+ tokens down to ~630 tokens (2,520 chars, ~70% reduction in base schema size).
  - Contains strictly the TypeScript discriminated union definitions (`UserAction`, `IntentResult`), Tier 1 global precedence rules (`OPT_OUT`, `REQUEST_HUMAN_CALL`, `BROCHURE_REQUEST`, `MAP_REQUEST`, `ASK_FAQ`), and JSON formatting directives.
- **Stage-Conditioned Micro-Prompt Generator (`buildStageMicroPrompt`):**
  - Evaluates `currentState` or `lead?.state` and returns ~350-450 tokens containing only the stage-relevant extraction rules, field targets, and 2-4 focused few-shot exemplars:
    - `ROLE_SELECTION_PENDING` / `FRESH`: 1 (Buy/Rent) vs 2 (Sell/Lease) vs 3 (Both); direct property type queries ("2 BHK", "flat in Gotri") route to `CHANGE_REQUIREMENT` (SEEKER); direct seller queries ("maro flat vechvo che") route to `SUBMIT_LISTING` (OWNER).
    - `OWNER_*_PENDING`: Owner intake extraction rules; single-digit mapping for possession ("1" -> READY_TO_MOVE, "2" -> UNDER_CONSTRUCTION) and furnishing ("1" -> UNFURNISHED, "2" -> SEMI_FURNISHED, "3" -> FURNISHED); area units (1 Var = 9 sqft); phone number extraction into `contact_phone`.
    - `QUALIFYING`: 3-turn compound qualification rules; rental terminology ("bhade", "bhadu", "reva mate", "kiraya", "rent" -> RENT); monthly budget vs capital purchase.
    - `OPTIONS_SENT` / `VISIT_REQUESTED` / `SITE_VISIT_PROPOSED`: Option selection indices (0, 1, 2) and slot booking formats.
    - `SITE_VISIT_DONE` / `SITE_VISIT_BOOKED` (post-visit): Attendance survey ("1" -> attended: true, "2" -> attended: false / CANNOT_ATTEND_VISIT); feedback vs alternative inventory requests.
    - `CRITERIA_CONFIRMATION_PENDING`: Confirmation ("1" -> confirm: true, "2" -> confirm: false).
    - `OWNER_DETAILS_GATHERED`: Decline 2nd listing ("nahi" -> GENERAL_QUERY decline, never OPT_OUT) vs listing a 2nd property vs buyer search.
- **Context Integration:**
  - `buildLeadContextForClassifier` incorporates active persona, detour state (`metadata.suspended_state`), and appends the stage micro-prompt.
  - Both Groq (`classifyLeadIntentWithGroq`) and Gemini (`classifyLeadIntentWithGemini`) call the lean core system prompt with stage-conditioned micro-prompt context.
  - Overall per-turn prompt overhead reduced by 53-64% (well below the 1,000-token cap).

### 2. State-Specific Modules & Zero-Numeric-Collision Token Trees
- **BHK vs Option 2 Collision Guard:**
  - Implemented `isBhkOrPropertyConfiguration`: boundary-checked token tree isolating BHK configurations (`1-5 BHK`, `RK`, `flat`, `apartment`, `villa`, `commercial shop`, `plot`, etc.) from isolated numeric choices.
  - In `ROLE_SELECTION_PENDING`, user replies like "2 BHK" or "2bhk in Gotri" contain the digit 2, which previously caused loose numeric checks to falsely classify as Option 2 (OWNER / `SUBMIT_LISTING`). Now, `isBhkOrPropertyConfiguration` and `disambiguateNumericChoice` strictly enforce `CHANGE_REQUIREMENT` (SEEKER) at both LLM validation and deterministic fallback layers.
- **Gujarati Numeral Normalization:**
  - Implemented `normalizeGujaratiDigits`: maps Indic numerals (`૧` -> 1, `૨` -> 2, `૩` -> 3, `૪` -> 4, `૫` -> 5) before token evaluation.
- **State-Specific Disambiguation (`disambiguateNumericChoice`):**
  - `OWNER_POSSESSION_PENDING`: "1" -> READY_TO_MOVE, "2" -> UNDER_CONSTRUCTION.
  - `OWNER_FURNISHING_PENDING`: "1" -> UNFURNISHED, "2" -> SEMI_FURNISHED, "3" -> FURNISHED.
  - `SITE_VISIT_DONE`: "1" -> CONFIRM_VISIT_ATTENDANCE (attended: true), "2" -> CANNOT_ATTEND_VISIT (attended: false).
  - `CRITERIA_CONFIRMATION_PENDING`: "1" -> CONFIRM_CRITERIA (confirm: true), "2" -> CONFIRM_CRITERIA (confirm: false).
  - `OPTIONS_SENT`: "1", "2", "3" -> SELECT_OPTION (index 0, 1, 2).
- **Vernacular Token Trees:**
  - `VERNACULAR_RENTAL_REGEX`: Boundary-checked matches for `bhade`, `bhadu`, `bhada par`, `bhade thi`, `reva mate`, `kiraya`, `rent par`.
  - `VERNACULAR_SALE_REGEX`: Boundary-checked matches for `vechva`, `vechvu`, `vechvo`, `bechna`, `bechni`, `sale`, `bikri`.
- **Validation & Fallback Synchronization:**
  - Guarded `validateUserAction` for `SUBMIT_LISTING` against BHK configurations.
  - Wired `disambiguateNumericChoice` and `isBhkOrPropertyConfiguration` into Tier 3 deterministic fallback in `classifyLeadIntent`.
