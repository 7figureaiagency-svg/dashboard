# Phase 27.2 Summary: Conversational Side-Question Interception, Seamless State Resumption & Multi-Entity Draft Archival

## Execution Overview

Plan 27.2 implemented conversational detour interception with instant single-turn state resumption (`metadata.suspended_state`) for in-flight FAQs during owner intake and buyer qualification. It also delivered multi-entity draft archival (`metadata.completed_submissions[]` and fresh `owner_draft`) and secondary buyer search preservation (`metadata.seeker_profile.searches[]`) with zero data wipes or state deadlocks.

## Key Achievements

### 1. Conversational Detour Interception & Instant State Resumption
- **Detour State Detection:**
  - Detects `intent === "ASK_FAQ"` across active intake states (`OWNER_*_PENDING`, `QUALIFYING`, `ROLE_SELECTION_PENDING`, `OPTIONS_SENT`, `VISIT_REQUESTED`).
  - Records active context into `metadata.suspended_state`:
    - `previous_state`: active state before the question.
    - `suspended_at`: timestamp of interruption.
    - `intake_type`: "OWNER" or "SEEKER".
    - `pending_field`: active question type derived by `deriveBotQuestionType`.
- **Dual-Payload Single-Turn Resolution in `handleFaqResponse`:**
  - Answers the specific FAQ query accurately (`OFFICE_ADDRESS`, `OFFICE_TIMINGS`, `AGENCY_INFO`, `RERA`, `BROKERAGE`, `LOAN`, `CUSTOM_FAQ`).
  - Suppresses the default generic site visit CTA (`bridgeCta = ""`) during in-flight intake detours to avoid disjointed sales pitches.
  - Appends a stage-aware resumption prompt via `buildDetourResumptionPrompt(targetState, lead, lang)` asking for the exact pending field in the user's active language (`GUJLISH`, `HINGLISH`, `ENGLISH`).
  - Maintains `nextState: targetState` and returns `leadUpdates` preserving existing `owner_draft` and `seeker_draft`.
- **Post-Detour Resumption Cleanup:**
  - `buildOwnerLeadUpdates` automatically clears `suspended_state: null` when the resumed intake question is answered, leaving the draft clean.

### 2. Multi-Entity Draft Archival & Multi-Search Preservation
- **Multi-Entity Owner Draft Archival:**
  - In `handleOwnerFlow`, when an intake completes and transitions to `OWNER_DETAILS_GATHERED`:
    - Formats a completed snapshot with `submission_id`, `completed_at`, `transaction_type`, `property_type`, `project_or_society`, `location`, `price_or_rent`, `carpet_sqft`, `possession_status`, and `furnishing_status`.
    - Pushes to `metadata.completed_submissions[]` and syncs with `metadata.archived_submissions[]`.
  - When user in `OWNER_DETAILS_GATHERED` requests to list an additional property ("2", "ek aur flat bechna hai", "commercial shop rent par deni hai"):
    - Preserves `metadata.completed_submissions` array completely intact.
    - Initializes fresh `owner_draft = { attributes: {} }`.
    - Resets `submission_id = null` and advances cleanly to `OWNER_SOCIETY_PENDING` or `OWNER_CONFIG_PENDING`.
- **Multi-Search Buyer Lifecycle Preservation:**
  - In `handleQualificationCascade` and `SITE_VISIT_BOOKED`:
    - When a qualified lead with an existing booked site visit initiates a secondary search (`intent === "CHANGE_REQUIREMENT"` or mentions a new property type):
      - Preserves `site_visit_booked: true`, `site_visit_at`, and `site_visit_datetime` intact.
      - Archives the previous search criteria into `metadata.seeker_profile.searches[]`.
      - Updates `metadata.seeker_profile.has_active_booked_visit = true` and tracks new requirements in `metadata.seeker_profile.current_search`.
