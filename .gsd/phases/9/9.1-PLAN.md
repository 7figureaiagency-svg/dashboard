# Plan 9.1: Database Multi-Tenant RLS Hardening & `current_client_id()` Security Function

## Objective
Implement strict PostgreSQL Row Level Security (RLS) enforcement at the database level by creating the `public.current_client_id()` security definer function and updating all tenant-scoped table policies (`leads`, `inventory`, `executives`, `property_submissions`, `lead_events`, `site_visits`, `clients`). When Griham Realty user (`kashyap@gmail.com`) queries the database, PostgreSQL strictly filters out Nextgen Realty records, while preserving `service_role` access for Edge Functions and background workers.

<task type="auto">
  <name>Task 1: Create `public.current_client_id()` Security Definer Function</name>
  <files>
    supabase/migrations/20261024000001_strict_multi_tenant_rls_isolation.sql
  </files>
  <action>
    Create and execute the security definer function `public.current_client_id()`:
    ```sql
    CREATE OR REPLACE FUNCTION public.current_client_id()
    RETURNS uuid
    LANGUAGE sql
    STABLE
    SECURITY DEFINER
    SET search_path = public
    AS $$
      SELECT client_id FROM public.profiles WHERE id = auth.uid()::text LIMIT 1;
    $$;

    GRANT EXECUTE ON FUNCTION public.current_client_id() TO authenticated, anon;
    ```
    This function looks up the authenticated user's `client_id` from `public.profiles` using their `auth.uid()`, running with `SECURITY DEFINER` privileges to prevent recursive RLS lookup locks.
    AVOID: Omitting `SET search_path = public`, which can open search path hijacking risks.
    USE: `STABLE` function qualifier so PostgreSQL caches the tenant ID lookup per transaction.
  </action>
  <verify>
    Execute SQL check:
    ```sql
    SELECT proname, prosecdef FROM pg_proc WHERE proname = 'current_client_id';
    ```
    Verify output returns `prosecdef = true`.
  </verify>
  <done>
    `public.current_client_id()` exists and is accessible to authenticated sessions.
  </done>
</task>
